## Results

### Unit suite

**19/19 passed**, plus a bridge protocol smoke test. Coverage:

- standard profile matches canonical keywords;
- normalized AST equivalence across all four profiles;
- keyword-only token conversion preserves comments and identifiers;
- profile rejection codes for duplicate, unknown, reassigned, missing, version, form, and type-collision errors;
- arithmetic precedence;
- i32 boundaries, checked overflow, minimum literal;
- short-circuit avoids a failing right operand;
- export/reimport preserves comments and applies edits;
- reimport rejects stale canonical bases and changed profiles;
- successful import refreshes the manifest for the next cycle;
- malformed manifests produce diagnostics instead of exceptions;
- export refuses to overwrite canonical source;
- interpreter rejects non-i32 harness arguments;
- BOM-prefixed source is accepted;
- leading zeros and grouped comparisons follow the core rules;
- generated target names are deterministic and independent of source names;
- bridge protocol: ping, four-target analysis, invalid syntax, malformed request, graceful shutdown.

### Conformance suite

**PASS: 0 failed, 0 blocked.**

- 29 positive cases.
- 4 profiles: `standard`, `my-syntax`, `terse`, `casual`.
- 4 targets: C#, Rust, Go, Java.
- 464 target executions (29 × 4 profiles × 4 targets).
- 27 negative cases: 20 program diagnostics + 7 profile-validation diagnostics.
- Each positive case also verifies:
  - reference outcome against independently specified expectations;
  - structural AST equivalence for every profile;
  - exact round-trip text preservation for every profile.

Reports:

- `reports/conformance.json` (machine-readable);
- `reports/conformance.md` (human-readable tables and failure details).

Pinned failure-node checks are included for addition, subtraction, multiplication, and negation overflow cases, so a backend cannot emit a generic `node: 0` and still pass.

## Independent review

Two independent code reviews were run against the implementation:

- frontend, profile conversion, semantics, interpreter, and export/import;
- backends, harness, CLI, and conformance reporting.

They performed differential fuzzing and targeted reproductions. Confirmed defects were fixed and re-verified:

1. import left the manifest stale after applying an edit (fixed: refresh canonical/personal fingerprints);
2. the reference interpreter accepted out-of-range/non-integer arguments (fixed: validate i32 arguments and CLI `--args`);
3. malformed manifests threw `TypeError` (fixed: validate manifest shape, emit `E_IMPORT_MANIFEST`);
4. export could overwrite the canonical source/profile (fixed: `E_EXPORT_PATH` guards);
5. Java rejected unreachable statements emitted after a return (fixed: omit unreachable statements);
6. conformance could report PASS with zero profile rows (fixed: require profiles; interpreter-only mode is explicitly labelled);
7. runtime error nodes were not compared (fixed: parse requires `node`, runner compares target nodes with reference nodes and pinned expectations);
8. process exit status was ignored once an outcome line existed (fixed: success must exit 0, failure must exit non-zero);
9. mixed-precedence comparison chains were not rejected (fixed: grouped-expression tracking; explicit parentheses still permit Boolean equality);
10. toolchain detection could classify an old .NET/Go SDK as a generated-code failure (fixed: version gates produce blocked results);
11. profile core-version diagnostic printed the wrong value (fixed);
12. imports did not cross-check the personal file named by the manifest (fixed);
13. leading-zero forms of the minimum literal were rejected (fixed);
14. BOM-prefixed input failed (fixed);
15. rejected declarations caused follow-on `E_UNKNOWN_NAME` diagnostics (fixed);
16. parenthesized expressions lost their inner diagnostic span (fixed).

## What did not run

- Visual Studio Code interactive UI verification (the extension is packaged and installed, but editor rendering and webview behavior were not driven by an automated UI test).
- No continuous-editor or language-server (LSP) verification beyond the included VS Code extension.
- No performance benchmarking beyond the committed editor latency budgets; no target-project build/run benchmark and no memory profiling.
- No cross-platform run: verification is on Windows x64. Generated projects use portable source but the build/run paths were only executed there.
- No committed property-based fuzzing. Review-time fuzzing was not retained as a repeatable script.
